### Teil 2 – Warum Web-Anwendungen?

📘 Klassisches **Deployment** heißt Installation per CD oder Download. Eine Web-Anwendung wird dagegen vom Server geladen
(V1, Folien 20–21). Im einfachsten Bild gibt es zwei Rechner: den **Client** und den **Server** (V1, Folie 22).

📘 Warum der Server oft mehr tun muss als Dateien auszuliefern, zeigt eine Suchmaschine: Für jeden denkbaren Suchbegriff eine
fertige HTML-Seite bereitzuhalten ist unmöglich. Stattdessen fragt ein **Serverskript** eine **Datenbank** ab und erzeugt
daraus eine HTML-Seite (V1, Folie 23). Typische Server-Sprachen sind PHP, Perl und Java. Java ist **nicht** JavaScript.

📘 Google macht dagegen schon beim Tippen Vorschläge. Das passiert **clientseitig** mit JavaScript im Browser (V1, Folie 24).

### Teil 3 – Drei Software-Architekturen

📘 Wo wird programmiert? (V1, Folien 25–27)

| Architektur | Wo läuft das Programm? | Beispiele aus dem Skript |
|---|---|---|
| alles **client-seitig** („Rich/Thick Client“) | im Webclient, der Server liefert nur aus | Java-Anwendung per Java Web Start |
| alles **server-seitig** | auf dem Webserver, der Browser zeigt nur an | Java Servlets, CGI, PHP |
| **beide Seiten** | Skripte im Browser **und** Programme auf dem Server | JavaScript im Browser + PHP/Java EE/CGI auf dem Server |

📘 Typische Aufgaben auf der **Client-Seite** (Folie 27): Grafik-Animationen, Formulare anpassen, Eingaben auf Plausibilität
prüfen, lokale Dialoge, asynchrone Interaktivität. Das Bild, das der Browser anzeigt, heißt **Document Object Model (DOM)**.
JavaScript ändert die Seite über das DOM. Auf der **Server-Seite** erzeugen Programme dynamische Seiten und binden Datenbanken,
Unternehmensanwendungen und externe Server an.

✏️ Meine Skizze dazu: Der Webclient (Browser) hat eine **Anzeige** und ein **Dokument (DOM)**. Vom Webserver kommt HTML, entweder
eine statische HTML-Seite oder eine dynamisch erzeugte Website, die mit Datenbank, externer Anwendung oder externem Server spricht.
Ein Skript im Browser kann z. B. eine Prüfung übernehmen, ohne erst den Server zu fragen.

✏️ Learnings aus der Stunde: Warum Projekt- und Objektorientierung? Weil wir Menschen in Objekten denken (Tisch, Fenster …).
Und: Ich wusste nicht, dass **Seiten in verschiedenen Browsern unterschiedlich aussehen**. Deshalb muss man testen.

### Teil 4 – Was ist eine Skriptsprache?

📘 Man unterscheidet **Programmiersprachen** (Java, C++, C, Assembler, Fortran), **Auszeichnungssprachen** (HTML, XML) und
**Skriptsprachen** (V1, Folie 29).

📘 **Übersetzung:** Ein Übersetzer (Compiler) wandelt das ganze Programm vorab in eine Zielsprache um, meist Maschinensprache
oder Bytecode für die JVM. Er prüft dabei die **statische Semantik** (Bindungs- und Typregeln) und findet viele Fehler vor der
Ausführung (Folie 30).

📘 **Interpretation:** Ein Interpretierer liest das Programm und führt es direkt aus. Regeln werden erst zur Laufzeit geprüft,
nicht ausgeführte Teile bleiben ungeprüft. Manche Interpretierer, z. B. für PHP und JavaScript, erzeugen vorher eine interne
Darstellung und prüfen so doch einiges vorab. Interpretierer lassen sich in andere Software einbauen, z. B. in den Browser.
Dafür kann Interpretation langsamer sein (Folie 31).

📘 Skriptsprachen lösen **kleine Aufgaben** durch das Zusammensetzen vorhandener Funktionen. Sie sind einfach (wenige Regeln,
kurze Programme), dynamisch typisiert, leicht erlernbar und stammen von den Kommandosprachen der Betriebssysteme. Beispiele:
PHP, Perl, JavaScript, Python, Ruby (Folien 32–33).

✏️ Meine Gegenüberstellung:

| Skriptsprache | Programmiersprache |
|---|---|
| interpretiert, Zeile für Zeile | Quellcode wird in die Zielsprache übersetzt, z. B. für den Prozessor |
| einfache Struktur, **keine** statische Struktur | statische Semantik: Passen Daten und Datentypen zusammen? |
| Prüfung erst bei der Ausführung | Prüfung durch den Compiler |
| Herkunft: Betriebssysteme, kurze Befehlsketten | „Compiler-Sprache“ |

✏️ Meine Randnotiz: **Heute** sind Skriptsprachen eigentlich genauso schwer wie Programmiersprachen und können das Gleiche.

### Teil 5 – JavaScript

📘 JavaScript ist eine „relativ“ einfache Skriptsprache, **extra für HTML entwickelt**. Der Code steht im `<script>`-Tag direkt im
HTML, wird zusammen mit dem HTML über **HTTP** vom Webserver geladen und im Browser **interpretiert**. Es ist „die“
Programmiersprache im Web und die Basis für dynamisches HTML und Web 2.0 (V1, Folie 35).

✏️ JavaScript wird heute überall im Browser genutzt und ist die meistgenutzte Programmiersprache für Webanwendungen weltweit.
JavaScript reagiert vor allem auf **Events**, also auf Benutzer-Ereignisse (wie ein „Action Listener“ in Java).

📘 **Die grundlegende HTML-Datei** (Folien 36–37): HTML besteht aus **Tags** in spitzen Klammern. Der Text zwischen `<title>` und
`</title>` erscheint in der Titelleiste des Browsers, der Text zwischen `<p>` und `</p>` auf der Seite.

✏️ `<head>`: Titel, wird nicht auf der Seite angezeigt. `<body>`: wird in der Webanwendung angezeigt. Der Browser baut daraus
einen Baum: `html` → `head` und `body` → `title` und `p`. Das ist das **DOM**.

📘 **Das erste JavaScript-Programm** (Folien 38–40): `alert("…")` im `<script>`-Tag öffnet ein Hinweisfenster, sobald die Seite
geladen wird. Die Datei muss trotzdem auf `.html` enden, denn es bleibt eine HTML-Datei, nur mit eingebautem JavaScript.
Die Befehle eines Programms heißen **Quellcode**.

📘 **Einfache Berechnungen** (Folien 41–42): `alert(17 + 5 * 3)` zeigt `32`, weil Punkt vor Strich gilt. Mit Anführungszeichen
(`"17 + 5 * 3"`) würde der Text unverändert ausgegeben.

📘 **Auf Benutzereingaben reagieren** (Folien 43–46): Benutzereingaben lösen **Ereignisse** aus. Mit dem Attribut `onclick` legt
man einen **Event-Handler** fest: JavaScript-Code, der beim Klick ausgeführt wird. Weil der Code in einem HTML-Attribut steht, muss
er in Anführungszeichen stehen. Innen und außen braucht es **unterschiedliche** Anführungszeichen: `onclick="alert('Hallo!')"`.

📘 **Kommentare** (Folien 47–48): Der Computer ignoriert sie. Sie machen Code lesbarer, für andere und für mich selbst in ein paar
Monaten. Einzeilig mit `//`, mehrzeilig zwischen `/*` und `*/`.

📘 **`<noscript>`** (Folien 49–50): Nicht jeder Browser führt JavaScript aus, manche Leute schalten es ab. Der Inhalt von
`<noscript>` erscheint **nur**, wenn kein JavaScript läuft, z. B. ein Hinweis oder besser ein Link auf eine Version ohne JavaScript.

✏️ Zum Schluss notiert: **Single Page Application / Multi Page Application**.

> ❓ **Offen:** Zu Single/Multi Page Application steht nur das Stichwort in meiner Mitschrift. Was genau dazu gesagt wurde, fehlt.

> 🤖 **KI-Erklärung – Single vs. Multi Page Application:** Bei einer **Multi Page Application** lädt jeder Klick eine neue
> HTML-Seite vom Server. Bei einer **Single Page Application** bleibt die Seite geladen, und JavaScript tauscht nur Teile des
> DOM aus. Dieses Portfolio ist eine Mischung: Die Kapitelseite `kapitel.html` bleibt gleich, JavaScript lädt den Inhalt der
> jeweiligen Vorlesung nach.

## Beispiele

📘 Das erste Programm, `hallo2.html` (V1, Folie 38):

```html
<!DOCTYPE html>
<html>
<head>
  <title>Hallo Welt!</title>
</head>
<body>
  <p>Das ist HTML.</p>
  <script type="text/javascript">
    alert("Hallo Welt! Das ist JavaScript.");
  </script>
</body>
</html>
```

📘 Reaktion auf einen Klick, `hallo5.html` (V1, Folie 44). Außen doppelte, innen einfache Anführungszeichen:

```html
<form>
  <input type="button" value="Test" onclick="alert('Hallo!')">
</form>
```

🤖 Punkt vor Strich und der Unterschied zwischen Rechnung und Text. Statt `alert` hier mit `console.log`, damit du es direkt
ausprobieren kannst:

```js
console.log(17 + 5 * 3);     // 32 – erst 5 * 3, dann + 17
console.log((17 + 5) * 3);   // 66 – Klammern zuerst
console.log("17 + 5 * 3");   // 17 + 5 * 3 – in Anführungszeichen ist es nur Text
```

📘 Kommentare (V1, Folien 47–48):

```js
console.log("Befehl 1"); // Dies ist ein Kommentar

/* Dies ist ein mehrzeiliger Kommentar.
   Befehle, die innerhalb eines Kommentars stehen,
   werden vom Browser nicht beachtet.
console.log("wird nie ausgegeben"); */

console.log("Befehl 2");
```


🤖 **JavaScript ausschalten in Chrome:** Entwicklertools öffnen (Mac: `⌘ + ⌥ + I`, Windows: `F12`), dann `⌘ + ⇧ + P`
(Windows: `Strg + ⇧ + P`), „Disable JavaScript“ eintippen, Enter, Seite neu laden. Ergebnis: kein Hinweisfenster, dafür steht
„Diese Seite benötigt JavaScript.“ auf der Seite. Solange die Entwicklertools offen sind, bleibt JavaScript aus.

🤖 Tipp: Probier das auch einmal mit diesem Portfolio. Ohne JavaScript bleibt die Startseite lesbar, nur die Kapitel werden nicht
geladen, weil sie per `fetch()` nachgeladen werden.
